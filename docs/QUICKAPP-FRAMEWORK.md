# 快应用框架

> 本阶段的唯一目标：把**快应用**这套框架服务做扎实。控制面板、页面设计、商店业务都不在本阶段。

**三处容易搞混的边界，先记牢**：

1. **快应用框架 ≠ 应用市场。**市场是**控制面板**里的一个功能，由控制面板这个系统快应用
   承载。框架只提供「装与不装」的能力，不决定「从哪儿装、装什么」。
2. **控制面板 ≠ 市场。**控制面板是预装的第一个系统快应用，它**里面**才有市场；
   它自己不在市场里，且走 OTA 更新，与市场更新分开。
3. **快应用 ≠ 免安装。**「免安装」免的是 Android 的 APK 安装，程序在 LobOS 内照样要装。

---

## 1. 什么是快应用

快应用是 **LobOS 里所有应用程序的形态与运行环境**，是一套**标准的框架服务**，
对标微信小程序 / 抖音小程序 / 各家快应用框架。

它不是某一个应用，而是**所有应用赖以存在的那层底座**。控制面板是它的第一个使用者，
以后每一个程序都在它上面跑。

### 与各家小程序的异同

| | 微信 / 抖音小程序 | **LobOS 快应用** |
|---|---|---|
| 安装 | 即开即用，没有安装过程 | **必须装** —— 走 LobOS 自己的安装逻辑（`ProgramInstaller`） |
| 更新 | 平台推送 | 走市场：开发者仓库 → 收录 → 提交更新 → 抓取（**市场是控制面板的功能，不是本框架**） |
| 桌面图标 | 有 | 有，**借 Android 的能力生成**（我们跑在 Android 上，不另造一套） |
| 入口来源 | 平台内的应用中心 | **只有控制面板里的市场**，不提供其他通道（**同上，市场不属于本框架**） |

**一处关键差异要记牢**：快应用**有**完整的安装逻辑。
「免安装」免的是 **Android 的 APK 安装**（不装 APK、不走 `PackageInstaller` 装应用），
不是免掉安装本身。程序在 LobOS 内照样装、照样落位、照样有版本。

---

## 2. 为什么要独立于 APK 安装

这是整个产品结构的根因，不是实现偏好。

```
Android 应用     装 APK     → 要重装 APK 才能装新应用
LobOS 快应用     装程序包   → APK 完全不动
```

因为程序的装、改、删全在 LobOS 内闭环，**APK 那一层永远不需要因为业务而变更**。
于是 APK 的更新面可以做到最小 —— APK 只做服务与逻辑，界面只留系统运行状态和一个入口。

这条因果链不能反过来：**不是"我们想让 APK 小"，而是"程序不经过 APK 安装"，
才使 APK 可以小。** 任何把业务/交互塞进 APK 的做法，都会破坏这个前提。

## 3. 现状基线（带取证）

这一节区分**已有**与**未有**。写清楚是为了不让后来的开发误以为"文档写了就等于做了"。

### 3.1 已有 —— 程序机制，真机走通过

| 能力 | 代码位置 |
|---|---|
| 程序清单校验 | `os/ManifestSchema.kt`（schema 3） |
| 安装（验签 → 落位） | `ota/ProgramInstaller.kt`、`ota/ProgramVerifier.kt` |
| 验签 | `assets/node/program-verify.js`（Ed25519 + 协议版本） |
| 升级与回滚 | `ota/ProgramOtaStateStore.kt`（`CURRENT` / `FLOOR` / `PENDING`）、`ProgramOtaUpdater.kt` |
| 旧版本清理 | `ota/ProgramDir.kt` 的 `pruneOldVersions` / `sweepStaleStaging` |
| 生命周期 | `runtime/InstanceHost.kt`（起停、wake lock、boot loop、端口、健康检查） |
| 能力声明 | `ManifestSchema` 的 `requires` / `capabilities` |
| 状态与迁移 | `os/ProgramManager.kt`、`ProgramStatus.kt`、`ProgramMigration.kt` |

**实证**：设备上程序装成并跑通过 —— 有 `CURRENT` 指针、程序清单声明 `requires`、
端口带健康检查。装与起这条链是真跑过的。

> **别把设备上的状态当范例**：那台机器上 `programs/console/` 下同时躺着
> `.51` / `.52` / `.53` 三个版本，而 `CURRENT=.53`、`FLOOR=.51` —— `.52` 既不是当前
> 也不是回滚地板，是一次中断/调试的残留。**那不是设计，是遗留。**
>
> **回滚窗口这套逻辑目前没有真机验证**：它只在代码里（`pruneOldVersions` 从未在
> 真机上正常清理过）。写现状时不能把它算成「已验证」。

### 3.2 升级语义：就地替换，不是多版本共存

**应用程序和工具链的升级语义是一致的：就地替换。**

| | 升级 | 旧版本去向 | 失败时 |
|---|---|---|---|
| 应用程序 | 新版本装上即是新版本 | 只在**回滚窗口**内暂存，过窗清理 | 装不上就是装不上 |
| 工具链 | 就地替换（先挪 `.retired`，落新成功才删旧） | 同上 | `soft` 档件可降级（少个 git 照样用） |

`CURRENT` / `FLOOR` / `PENDING` 三个文件是**回滚机制**，不是共存机制：
`CURRENT` 当前在跑、`FLOOR` 可回退到的地板、`PENDING` 正在装还没切换的。

**唯一的差别是失败语义**，而且这个差别是合理的：工具链是共享依赖，缺一个不致命；
应用是独立实体，起不来就是起不来。

### 3.3 未有 —— 缺口清单

| 缺口 | 取证 |
|---|---|
| **桌面图标** | 全仓 `shortcut` / `addShortcut` / `桌面图标` **零命中** |
| **快应用运行时** | `ui.type=quickapp` 在 `ManifestSchema` 里只有校验器，**无消费方**（`grep` 排除该文件后零命中） |
| **应用市场** | 不在本框架范围内（见 4.1）。市场由控制面板承载，不作为框架的缺口记在这里 |
| **能力 API 的档位闸** | `CapabilityTier` 分的是「我们这个 APK 拿到了多少权限」（`apk` / `apk+adb` / `apk+do`），**不是**「这个 API 开放给谁」。按对象分的闸未建 |

**一句话**：进程型程序（起进程、占端口、后台服务）这条线已建通；
**界面型快应用**（能被点开、有桌面图标、装完即可见）这条线尚未开始。

### 3.4 进程隔离与资源限制：做了什么、明确不做什么

这一条容易误解，所以写死。

**进程隔离要做，防的是稳定性问题：**

| 能力 | 状态 | 取证 |
|---|---|---|
| 后端独立进程 | **已有** | `ProcessSupervisor.spawn(owner = OWNER_PROGRAM)` |
| 一个崩了不带崩别的 | **已有** | 独立进程即得 |
| 卡死检测 + 自动拉起 | **已有** | `/status` 探活 → 连续失败 3 次 → 退出稳态循环 → 重启 + 退避（`SupervisorPolicy.HEALTH_FAIL_THRESHOLD = 3`） |

**明确不做：进程内资源限制。** 原 schema 里的 `isolation.memoryMax` /
`isolation.pidsMax` / `isolation.namespaces` 三个字段**已删除**。

删除的理由：

1. **它们从来没被执行过** —— schema 定义并校验，但全仓无任何代码读取或执行。
   留着就是「文档/schema 声称有、实际一行没跑」。
2. **内存上限挡不住的问题比挡住的更多**：上限内疯狂分配再释放（GC 抖动拖慢整机）、
   死循环打满 CPU、同步 IO 卡死、缓慢泄漏 —— 这些上限一个都拦不住。
3. **真正有效的隔离已经有**：崩溃隔离与卡死检测是独立进程带来的，Android 自身
   在进程级也提供了隔离。

**不要把它记成「还没做」而留成待办** —— 这是产品决策，不是缺口。
若将来真的需要（例如某个程序必须限内存），那时应当基于实测的失控场景来定阈值，
而不是先在schema 里预留一个没人执行的字段。

### 3.5 进程隔离 ≠ 安全边界

这是两件事，不要混：

- **进程隔离**：防崩溃、卡死、资源互相拖垮 —— **稳定性**，技术问题，本框架负责。
- **安全边界**：防恶意程序 —— **信任**问题，靠**分发闭环**（市场是唯一入口，
  每次提交与每次更新都经我们审批 + 验证 + 安全测试），**不做技术隔离**。

权限模型也是「一套共享」：LobOS 拿到 Android 权限，里面所有程序共享同一套，
不按 `programId` 分程序授权。`programId` 只用于**识别、审计、限流**。

## 4. 框架职责

快应用框架作为系统服务，至少要提供这些能力。每条都标注现状。

| 能力 | 说明 | 现状 |
|---|---|---|
| 安装 | 验签 → 落位 → 切 `CURRENT` → 旧版进回滚窗口 | **已有** |
| 桌面入口 | 装完生成桌面图标，可点开；借 Android 能力 | **未有** |
| 卸载 | 清实体、图标、状态、旧版本 | 待核（随图标一并做） |
| 运行时 | 起停、端口、健康检查、生命周期策略 | **已有** |
| 能力授权 | 按程序声明的 `requires` / `capabilities` 授 | 骨架已有，闸未建 |

### 4.1 两条供给通道：传输可共用，策略必须分开

系统里有两条装东西的路，**升级语义一致（都是就地替换），但管理策略不同**：

| | 工具链通道 | 程序通道 |
|---|---|---|
| 落位 | `usr/lib/toolchain/<件名>/` + `usr/bin/<名>` 符号链接 | `programs/<id>/<版本>/` + `CURRENT` |
| 粒度 | 按**件**（curl 一个、node 一个） | 按**程序**（一个应用一整包） |
| 失败 | `soft` 档可降级 | 装不上就是装不上 |
| 谁在用 | 任何程序都能用（共享依赖层） | 只有那个程序自己（独立实体） |

**为什么策略不能合并**：工具链是**全局共享的依赖层**，一个名字背后只能有一份，
就地替换是唯一正确解；程序是**各自独立的实体**，有生命周期、有状态、有依赖，
但它依赖的工具链是共享的 —— 硬合并就会出现「两个版本的程序要各锁一份 node」，
而 node 是全局一份，做不到。

**传输层可以复用**（取件 / 验签 / 逐件 sha256 / 解压 / 原子落位），
供给链那套「先挪后落、失败回退」是真踩过坑才定下来的，值得共用。
**管理策略各留各的。**

### 4.2 框架不做什么

**应用市场不在本框架内。**市场是**控制面板**里的一个功能，由控制面板这个系统快应用承载，
不是快应用框架的一部分。

框架只提供**装与不装的能力**（安装、更新、卸载、桌面入口、运行时、能力授权），
不提供**从哪儿装、装什么**的判断 —— 那是控制面板与市场的职责。

> 提一句边界外的背景，避免日后误读：市场里同时有系统组件（node、git、curl 等）
> 和应用程序（快应用）两类；历史上工具链走的是 OTA 那条路。
> 这些都属于控制面板与市场的范围，本框架不碰。

## 5. 程序形态

基于 `ManifestSchema`（schema 3）已定的字段。快应用与普通程序**共用这套清单**，
差异体现在 `ui` 与 `lifecycle` 上。

```
id            程序身份
version       版本
entry         入口
args / env    启动参数与环境
lifecycle     resident / restart / maxRestarts / backoff
http          port / health
requires      要哪些宿主能力
capabilities  能力细节
ui            type=quickapp / package / url / onUiClosed
```

（`isolation` 已删 —— 见 3.4「明确不做进程内资源限制」）

`ui.type` 只接受 `quickapp`；`onUiClosed` 三种语义：
`keep-alive` / `stop-with-ui` / `on-demand`。

`ui.package` 是 1:1 绑定的唯一标识，`ui.url` 只接受 http/https。

## 6. 边界：三类 API

产品的边界靠 API 维持，不靠约定。

| 类别 | 面向 | 现状 |
|---|---|---|
| **系统级** | LobOS 底层服务调用 | 分层意图有，**闸未建** |
| **程序集** | 普通开发者 | 同上 |
| **合作厂商** | 固定合作方 | 同上 |

**现状提醒**：`CapabilityTier` 的三档是「我们这个 APK 有多少权限」，
不是「这个 API 开放给谁」。这两件事不要混。

---

## 7. 控制面板在本框架里的位置

控制面板是**第一个系统快应用**，与市场里的应用有本质区别：

| | 市场里的快应用 | **控制面板** |
|---|---|---|
| 来源 | 开发者提交，我们收录 | **内置在 APK 里，预装** |
| 市场可见 | 是 | **否 —— 市场里没有这个应用** |
| 身份 | 普通程序 | **官方系统应用**（形态是快应用，位置也是快应用） |
| 能力面 | 声明式 | 调用系统私有 API，与系统打通 |
| 更新通道 | 市场抓取 | **OTA**（独立于市场） |

**所以只有控制面板走 OTA。** 工具链、系统组件走市场，不走 OTA。

## 8. 待决问题

写在这里而不是反复确认，是因为它们属于下一阶段，且都有可查证的技术前提。

1. **桌面图标的具体落法**：借 Android 哪个能力（`INSTALL_SHORTCUT` / launcher intent /
   自建 launcher）—— 等真机实验结果，不靠推测。
2. **市场本体何时开工**（属控制面板范围，非本框架）：它是控制面板里的一个功能模块，
   还是控制面板的第一个版本就先带上。
3. **工具链从 OTA 并入市场**的迁移路径与兼容期。
4. **三类 API 闸的具体判据**：每一类开放到哪一层，用什么证据判定"已验证"。
5. **快应用与控制面板共用清单但能力面不同**——是否需要在清单里区分「系统应用」标记。
