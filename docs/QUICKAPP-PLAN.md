# 快应用框架落地方案

> 配套：`docs/QUICKAPP-FRAMEWORK.md`（共识与现状基线）。本文只讲**怎么落地**。
> 文中每条决策都标注了取证来源；未取证的一律标「未验证」。

---

## 0. 方向（这一段是全文的前提）

**LobOS 是跑在 Android 里的虚拟 PC 系统。程序的「后端」由 LobOS 管，
「前端」由快应用服务框架提供。**

结果是：LobOS 里的每一个程序，在 Android 原生系统里都有了它自己的
生存状态——自己的图标、自己的窗口、能被点开、能切后台、能被系统记住。

**所以：快应用框架 = 程序的前端在 Android 里的载体。**
它不是某个应用，是**所有程序共用的底座**，所以必须是服务。

**主体是界面框架。**图标是末端表现，不是目标。

已建成（本仓已有，无需重做）：安装/验签/落位、程序索引、
起后端进程/保活/卡死拉起、升级/回滚/卸载、能力授权。

## 1. 为什么不用别人的引擎

调查结论（AOSP + 官方源核实）：

| 事实 | 影响 |
|---|---|
| **AOSP 没有快应用**（两个镜像搜 `quickapp`/`kuaiapp`/`QuickAppService` 零命中；对照组 `VirtualDeviceManager` 128 命中，证明搜索有效） | 没有原生底座可抄 |
| 唯一开源实现 `hapjs-platform/hapjs` 的 **V8 是 EPL-1.0**（其 `NOTICE` 里 `jsenv-runtime` 明确标注） | 闭源产品不能直接用 |
| 需 vendoring 3500+ 文件；要求 `:Launcher*` 进程约定；`getToolsJar()` 在 JDK 17 直接失败 | 集成成本与风险都高 |
| 它的包是**纯 Java 928 文件**（无 Kotlin） | 这一条是好消息，但不足以抵消上面三条 |

**结论：不嵌入 hapjs。**我们自建界面框架；逻辑层复用**已在的 node（V8）**，
不引入第二个 JS 引擎。

## 2. 界面框架（本阶段主体）

### 2.1 最小范围（先跑通「点开是个真应用」）

**页面描述 → Android 原生控件。**快应用包带自己的页面，框架把它渲染出来。

| 能力 | 说明 |
|---|---|
| 页面描述 | 快应用包里带页面定义（格式见 §5.1 待定项） |
| 组件 | 文本、图片、按钮、输入框、列表、纵向/横向容器、滚动容器 |
| 样式 | CSS 子集：字号、颜色、边距、圆角、背景、flex 主轴/交叉轴 |
| 布局 | flex（各家共同模型；hapjs 用的是 Facebook Yoga） |
| 导航 | 页面栈：入栈、出栈、替换、返回 |

**明确不在本阶段**：动画、web 组件、canvas、原生选择器、子包、热重载。

### 2.2 逻辑层：复用已有的 node

**不引入第二个 JS 引擎。**逻辑层用已在的 node（商店件 L1，V8）。

- 逻辑代码跑在 node 里 → 后端也是 node → **前后端同一运行时**，沟通可以最简单
  （同进程内直接调，或走已有的 bridge）。
- 这与微信「V8 逻辑层 + WebView 视图层」是同一个分层思路，
  只是我们的视图层用原生控件而非 WebView。

**待定**：逻辑层每个快应用各起一个 node，还是共用一个。
倾向前者（隔离干净，与后端一致），代价是每快应用一个进程。

### 2.3 窗口：每个程序有自己的

`QuickAppActivity`（已建骨架）+ 独立 `taskAffinity`：
点开它就是它自己，不是宿主的一个页面；系统能记住它、能切后台。

### 2.4 与后端的衔接

按已定模型：**前端不直接碰系统能力。**

```
快应用界面  →  快应用自己的逻辑（node）  →  LobOS 能力 API（bridge）
```

界面事件绑定到逻辑，逻辑调能力。走已有的 `CapabilityBroker`，不新增第二套。

## 3. 桌面入口（末端，但必须有）

已建 `QuickAppIcons` / `QuickAppDesktop` 骨架。两个 Android 硬约束（AOSP 核实）：

1. `requestPinShortcut` **必须用户确认**、**必须有前台界面**。
   → 入口是「程序界面里一个『添加到桌面』按钮」，不是「装完自动有」。
2. pinned shortcut **进不了 app 抽屉**，只在桌面。程序在桌面上有图标成立；
   要进应用列表只有一条路：它自己是已安装 APK —— 违背整个结构，不做。

**未做完的**：`QuickAppActivity` 的窗口里现在是诊断文字，不是真界面 ——
这正是本阶段要替换掉的部分。

## 4. 落地顺序

| 步 | 做什么 | 验什么 |
|---|---|---|
| 1 | **定页面描述的最小格式** | 格式能表达 2.1 的组件与样式；有可校验的 schema |
| 2 | 解析 → 组件树 | 一个示例页面能解析成树 |
| 3 | 组件树 → Android 控件 | 屏幕上是真界面，不是诊断文字 |
| 4 | 布局（flex） | 多组件排布正确 |
| 5 | 页面栈 | 入栈/返回/切换正常 |
| 6 | 界面事件 → 逻辑层（node） | 点按钮触发逻辑 |
| 7 | 逻辑 → 能力 API | 逻辑能调到 `bridge:*` |
| 8 | 「添加到桌面」接进安装完成 | 装完点一下能出图标 |

**步 1 之前不动代码。**格式定错，后面全废。
