# 组件规范：件从构建到运行的五个阶段

> 本文是**规格**：每阶段只回答一个问题，每个答案只有一个来源。
> 写它是为了在动手改代码之前把规范立起来 —— 否则改完还得再改。
>
> 核实日期 2026-10-08。文中每条结论都能追到 `文件:行号`。

---

## 序：为什么要立这个

现在的问题是「东一个西一个」：

```
zip 件       ProgramInstallPipeline → upsert        ✅
内置原生件   PrefixProvisioner       → 不 upsert      ❌
快应用       QuickAppRegistry        → mutate        只写 ui 字段
```

**三条安装路径，三套登记方式。** 内核为了照顾这个分裂，只能硬编码
「哪个件是 bash、哪个是 openssl」—— 9 处硬编码由此而来。

根因不是「注册表字段不够」，而是**没有一份「件」的规格**：
一件事该在哪一阶段定下来、由谁定、其它阶段怎么读 —— 都没写。

## 阶段一：构建 —— 「它是什么」

### 唯一真相：`scripts/component-sources.json`（钉值表）

| 项 | 谁填 | 内容 |
|---|---|---|
| `sources.<key>` | 人 | 版本 + sha256 + 下载地址 |
| `ndkVersion` | 人 | 交叉编译件用的 NDK |
| `llvmVersion` | 人 | 编 clang 用 |

### 规格

1. **一件东西的「身份」在构建期定死**：叫什么、什么版本、源码从哪来。
2. **构建期不产生运行时信息**（不落位、不依赖谁）。
3. 缓存 key 含全部依赖的版本 —— 依赖变了 tag 就变（`scripts/cache-key.sh`）。

### 现状核实

| 项 | 状态 |
|---|---|
| bash / busybox / zlib / openssl / curl / jq / make / cmake / pkgconf / llvm | ✅ 在钉值表 |
| ripgrep | ✅ 已补（形状不同：无 `urls`，`sha256` 由构建时建立基线） |
| node / npm | ⚠️ 在 `node-versions.json`（另一张表） |
| pnpm | ⚠️ 钉在 `build-component-pnpm.sh` 第一行 |
| libcxx | ⚠️ = `ndkVersion`，没有独立项 |

**待定**：后三项要不要并进钉值表？（我的看法：它们本来就不从同一处发版，
可以在钉值表里指来源，不必物理合并。）

## 阶段二：打包 —— 「它是什么字节」

### 唯一真相：文件名（内容寻址）

```
component-<件>-<版本>-<内容哈希12位>-android-arm64.zip
```

### 规格

3. **名字里的哈希必须与实际字节一致**，不符即构建失败（`package-component.sh:21-22` 命名 · `publish-component-manifest.js:122-123` 校验）。
4. **一份产物只在一个地方**：不进 `jniLibs`（node 那条断言已实现）。

### 现状核实

| 项 | 状态 |
|---|---|
| 内容寻址命名 | ✅ |
| `node 不入 APK` 断言 | ✅ `build-apk.yml` 有那一步 |

## 阶段三：发布 —— 「有什么可装的」

### 唯一真相：包外清单（`program-manifest.json` / `component-manifest.json`）

只回答「这一轮有没有新版可装」，**六个字段**：
`id` `name` `version` `url` `sha256` `signature`

### 规格

5. **包外清单不是启动契约**，它只回答「有没有新版」。
   启动契约（`entry`/`args`/`env`/`http`/`lifecycle`/`ui`）**不进包外清单**。
6. **防重放与过期是发布期的判据**：`sequence`（防旧清单重放）·
   `expiresEpochMs`（过期即拒用），由 `publish-component-manifest.js:180-181` 生成，不属于程序包（核实：`program-bundle.js` 里无这两个字段）。
7. **两路并存**：
   - GitHub Release —— 构建预制品（编一次长期复用）
   - 对象存储 —— 设备下载（`component/<zip 名>`）

### 现状核实

| 项 | 状态 |
|---|---|
| 包外清单瘦身成六个字段 | ✅ 本轮已做 |
| `sequence` / `expiresEpochMs` 由发布侧生成 | ✅ 不在包内（核实：`program-bundle.js` 无此字段） |
| 包内清单 = 启动契约 | ✅ 已在 zip 里 |

## 阶段四：装机 —— 「装完了」

### 唯一真相：注册表（`ProgramIndex`）

### 规格

8. **装机是唯一一次登记的时机**。登记的是「装的时候定下来、之后不变」的东西。
9. **凡是装进来的，都登记 —— 包括随 APK 内置的**。
10. **版本不是抄来的，是问出来的**：装完跑它自己（`InstalledRuntime.versionOf`），
    问不出来才回退到包内声明。**没装之前没人知道版本。**
11. **判「要不要装」用字节身份，不用版本**：本机落位那批字节的 sha256
    与清单相同 → 已是这批，不装。（版本号是声明，sha256 是事实）
12. **落位规则只有一个判据**（`ProgramManager.relStateDir:90-91`）：
    内核件落 `$PREFIX/lib` 与 `$PREFIX/bin`，不占 `stateDir`；
    其余落 `programs/<id>/`。

### 现状核实

| 项 | 状态 | 缺什么 |
|---|---|---|
| zip 件登记 | ✅ `ProgramInstallPipeline.upsert` | — |
| **内置原生件登记** | ❌ **不 upsert**（`PrefixProvisioner` 里 upsert 出现 0 次） | **这是 9 处硬编码的来源** |
| 快应用登记 | ✅ `QuickAppRegistry.mutate` | 只写 ui 字段 |
| 版本问出来 | ✅ 上一轮已改 | — |
| 按字节判更新 | ✅ 上一轮已改 | — |

## 阶段五：运行 —— 「怎么用它」

### 唯一真相：统一搜索路径 + 注册表

### 规格

13. **能力全局可用靠路径，不靠登记**（对照 `ld.so.conf` + `ldconfig`）：
    - 可执行件 → `$PREFIX/bin` 在 `PATH` 里
    - 共享库 → `$PREFIX/lib` 在库搜索路径里
    - **一律满足这一条就全局可用，不问「它是什么件」**
14. **运行期从注册表读运行逻辑**（怎么起、给什么环境、要哪些依赖）。
15. **内核不认识任何具体的件**：不硬编码 `bash`/`openssl`/`node`。

### 现状核实

| 项 | 状态 | 缺什么 |
|---|---|---|
| 统一搜索路径 | ✅ `RuntimeEnvironment.libSearchPath:111` | — |
| `$PREFIX/bin` 在 PATH | ✅ `PrefixProvisioner.binDir` | — |
| 内核不认具体件 | ❌ **9 处硬编码** | 阶段四补上登记即可消除 |

## 汇总：每阶段回答一个问题

| 阶段 | 问题 | 唯一真相 | 状态 |
|---|---|---|---|
| 构建 | 它是什么 | `component-sources.json` | ⚠️ 三处版本源待理 |
| 打包 | 它是什么字节 | 文件名（内容寻址） | ✅ |
| 发布 | 有什么可装的 | 包外清单（六字段） | ✅ |
| 装机 | 装完了 | 注册表 | ❌ **内置原生件没登记** |
| 运行 | 怎么用它 | 搜索路径 + 注册表 | ❌ 内核硬编码 9 处 |

## 待定的三件事

| # | 问题 | 我的看法 |
|---|---|---|
| 1 | **node/npm/pnpm 的版本要不要并进钉值表？** | 不必物理合并，但要在钉值表里**指明来源**（现在三处分散在两张表 + 一个脚本里） |
| 2 | **内置原生件登记后，字段与 zip 件完全一样吗？** | 应完全一样。若不一样，说明它不是「一件东西」，而是「系统的一部分」—— 那要重新想它该不该算「件」 |
| 3 | **`invalid` 这个字段（包不合法的原因）算不算「装的时候定下来的」？** | 算。它是装机校验的结论，不是运行时状态 |

## 这份规格解决了什么

立项时的问题「怎么解决硬编码」，答案在这份规格里只有一句：

> **规格第 9 条：凡是装进来的，都登记。**

内置原生件之所以被硬编码，是因为它**没登记**。
补上这一条，硬编码就没有存在的理由了 —— 内核问表即可。

**而补这一条不需要先改任何字段、不需要先定注册表的新结构** ——
所以规范立起来之后，第一步改动是安全的、可独立验证的、可随时退回的。
