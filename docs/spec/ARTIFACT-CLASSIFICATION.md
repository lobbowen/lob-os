# 产出物定位规范

本文件立的规矩只有一条：**任何产出物，先定位，再动手；定位不清的东西不进产品。**

---

## 1 一条总规矩

我们先做的是一个系统，不是一个工具的堆砌。系统里的每一样东西都必须有准确位置，
位置决定它的生命周期、分发方式和责任方。

定位不清就动手，结果就是「造了一个谁也不需要、谁也不依赖的空壳」——
这类东西不进产品。

---

## 2 三类产出物

### 2.1 宿主底座

**定位**：系统必备能力，缺了系统就不是这套系统。
**分发**：随 APK 内置，不是可安装件。
**责任方**：宿主实现（Android 进程内）。

当前属于这一类：

- `OsHostService` —— 系统主进程，前台常驻
- `CapabilityBroker` —— 系统能力总线（JSON-RPC 桥）
- `ServiceRegistry` 内置服务 —— `piece-*` / `prefix` / `view` / `pty` / `sysdev`
- 内核垫片、PtySession、LdConfig 等系统能力实现

**判据**：系统没有它就不能正常工作，且它不是用户可装卸的东西。

### 2.2 用户件

**定位**：可安装的用户可见能力（工具、库、运行时）。
**分发**：件系统管理，可安装/更新/回退。
**责任方**：件构建与 supply 链路。

当前属于这一类（9 件）：

| 类 | 件 |
|---|---|
| 必备（系统基础件） | bash busybox crypto curl openssl zlib |
| 能力（按需安装） | git jq ripgrep |

**判据**：用户可装卸、有明确用途、系统没有它仍能运行（只是少一个能力）。

### 2.3 测试夹具

**定位**：只用于验证机制，不是产品组件。
**分发**：不进 APK、不进件系统、不进清单。
**责任方**：验证过程临时持有，用完即弃。

**判据**：不提供系统缺的能力、没有真实依赖方、只为验证某个机制而存在。

---

## 3 定位判据（动手前必答）

任何新产出，动手前必须回答三个问题：

1. **系统没有它，能不能正常工作？**
   - 不能 → 宿主底座（随 APK 内置）
   - 能 → 看第 2 问
2. **用户是否需要装卸它？**
   - 是 → 用户件（件系统管理）
   - 否 → 看第 3 问
3. **它是为验证某个机制而存在的吗？**
   - 是 → 测试夹具（不进产品）
   - 否 → 定位不清，**不许动手**，先回来重新定义

---

## 4 反面案例（已发生，留作警戒）

**hostd（已撤销）**：

曾为「补一个服务实例」写了 hostd —— 一个只响应 `GET /status` 返回 200 的空壳。
按本节判据复核：

- 系统没有它能不能工作？**能**（系统靠 CapabilityBroker + 内置服务正常运行）
- 用户是否需要装卸它？**否**（没有任何依赖方）
- 是不是为验证机制而存在？**是**

结论：测试夹具，不进产品。且它想扮演的「系统服务」位置，宿主侧 CapabilityBroker
已经占了 —— 属于重复已有能力。

处置：源码、构建脚本、件包、以及为其加的构建改动（`LOBOS_STATIC`、ManifestWriter
透传 http）全部撤销。**不是为了补一个形式上的「服务实例」就造一个空壳。**

---

## 5 与服务相关的定位结论

「系统服务」在我们这套系统里的准确定位：

- **系统能力服务**：宿主侧提供（OsHostService / CapabilityBroker / 内置服务），
  随 APK 内置，是底座，不是件。
- **客侧常驻程序**：目前没有真实需求 —— 所有系统能力宿主已提供，客程序都是工具。

若将来出现真实需求（例如客侧包管理、跨进程服务、需要长期运行的业务 daemon），
按第 3 节判据重新定位；确认为宿主底座的，直接打包进 APK；
确认为用户件的，走件系统。**不预设立场，不先造壳。**
