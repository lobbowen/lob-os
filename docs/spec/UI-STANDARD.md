# LOB-OS 界面规范（草案 v1）

本文件定的是**产品界面**，不是调试面板。目标读者是使用者，不是工程师。

---

## 1 一条总规矩

界面上每一个状态，都必须对应一条**真实的、可复现的后端事实**。

- 不允许出现「看起来在装，其实没装」
- 不允许出现无法解释原因的禁用按钮
- 不允许把内部机制（URL、requestId、sha、APK 原件）直接暴露成界面用语
  （这些留在调试面板里，正常界面不出现）

每个状态都要能回答：**这是什么、为什么、我下一步能做什么**。

---

## 2 使用者模型

使用者把这台设备当成一台**机器**来用。他要的是：

1. 知道机器现在好不好用
2. 知道有什么、能装什么
3. 装东西时知道在做什么、卡在哪、失败怎么办
4. 装错了能退回去
5. 坏了能修

界面的信息架构就按这五条来，不按代码结构来。

---

## 3 四屏

### 屏 1 状态（Home）

一句话结论加三张卡。

| 区域 | 内容 | 后端事实 |
|---|---|---|
| 结论 | `运行正常` / `部分组件缺失` / `需要修复` | BootOutcome 与系统件就位判定 |
| 卡「已装」 | 组件数量 | InstallGuard.all 的条目数 |
| 卡「可更新」 | 有更新的数量 | 清单比对本机账本 |
| 卡「占用」 | 已用空间 | 账本字节数汇总 |

缺件时，结论行下面直接给「补齐」按钮，按钮点下去就是安装流程。

### 屏 2 组件（Components）

两栏：`已安装` 与 `可安装`。

已安装每项显示：名称、版本、大小、状态（正常 / 有更新 / 有故障）。
每项可展开，展开后显示：依赖了谁、被谁依赖、安装时间、来源。

可安装每项显示：名称、版本、大小、简介；点进去是安装页。

### 屏 3 安装（Install）

安装前必须给一张**将要发生什么**的清单：

- 会装哪几件（含自动带上的依赖）
- 总共多大
- 需要多少可用空间
- 装完之后哪些能力会可用

然后是四段进度：`下载` → `校验` → `落位` → `接入`。
每段都有明确的成功/失败，失败给人话与下一步。

### 屏 4 故障与恢复（Recovery）

- 自检结果（系统件、库链接、盘空间）
- 最近一次失败（人话摘要 + 详情折叠）
- 一键修复
- 回退到出厂

---

## 4 状态语言

状态必须是名词加形容词，不要动词进行时的假状态。

| 层 | 状态 | 含义 |
|---|---|---|
| 系统 | 正常 | 必备件齐、库链接齐、盘够用 |
| 系统 | 部分可用 | 缺非必备件，核心可用 |
| 系统 | 需修复 | 缺必备件或链接断开 |
| 组件 | 正常 | 落位与内容核验都过 |
| 组件 | 有更新 | 清单版本高于本机账本 |
| 组件 | 已损坏 | 内容核验不过 |
| 安装 | 等待 / 下载中 / 校验中 / 落位中 / 接入中 / 完成 / 失败 | 与安装管线四段一一对应 |

---

## 5 文案规范

1. 先说结论，再说原因，再给下一步。一句一条。
2. 不出现内部标识（id 可以出现但要在括号里作为补充）。
3. 失败文案必须包含「你可以做什么」。
4. 数字要带单位与量级判断（例如「需要约 120MB，当前可用 40MB」）。
5. 不使用感叹号与营销词。

---

## 6 视觉规范

- 深色底，前景高对比；等宽字体只用于路径与日志，不用于正文。
- 一张屏一个主动作，其余为次要。
- 列表项高度一致，图标位固定，状态用色 + 文字双编码（不只靠颜色）。
- 不允许在正文里出现调试字样。

---

## 7 与调试面板的关系

调试面板保留（工程师用），但：

- 它不再是产品的门面
- 正常界面里不出现它的入口，只有「关于」里一个入口
- 面板里的每一项都要能说明「它属于哪一条后端事实」

---

## 8 落地顺序

1. 屏 1 状态（依赖最少，先把「机器好不好用」说清）
2. 屏 2 组件（读账本与清单）
3. 屏 3 安装（接安装管线四段）
4. 屏 4 恢复（接自检与回滚）

每屏都先做「只有真实状态、没有假状态」的版本，再加细节。
