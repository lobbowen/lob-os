# LobOS 系统化设计概念候选

基于三份调研（设计感手法 / 非 tab 信息架构 / 系统工具设计语言）综合。
目标：给用户 3 个真正不同的"系统化概念"，每个都重新组织信息，不是换色、不是平铺 tab。
视觉全部受 `UI-DESIGN-SPEC-v1.md` 的 15 条审核清单约束。

---

## 共识：设计感从哪来（调研结论）

用户否掉前几版的根因不是配色，是"没有系统性的设计决策"。真正的设计感 = 克制里的精确度：
- 字阶/字重成系统（每级固定 size/line-height/字距/weight，无表外值）
- 每屏一个视觉焦点、强调色只给主操作
- 对齐可证明、图标与文字视觉重量匹配
- 留白有节奏（组内紧/组间中/层级间大）
- 边框只画一次、透明分层阴影
- 动效只解释因果，可打断
- 所有状态都设计过（空/加载/错误/密集/长文本/深色）

调研明确：不要把命令面板当完整主界面（它是入口不是主页）。

---

## 概念 A · 剖面房（Sectioned Rooms）

**一句话**：把系统当成一栋建筑，首页是"剖面总览"，各能力是房间，进入房间才看细节。

**主视图**：首屏是一张系统剖面图——垂直分层：
```
┌─ Agents ──── 应用层（agent 应用，可进入）
├─ Runtimes ── 运行时层（python/node，版本槽位在这里）
├─ Components ─ 组件/工具层
├─ Libraries ── 共享库层（ldconfig 视图）
└─ System ───── 状态/空间/控制面
```
每层是一行，右侧显示该层的状态摘要（几个版本/几个组件/占用空间），
轻点层展开为该层的管理视图（不是跳 tab，是同一界面的下钻）。

**四类内容如何容纳**：
- 商店 = 运行时层/组件层展开后的"可安装"视图
- 组件 = 组件层展开
- 空间 = 系统层里的容量视图，或剖面图右侧常驻的容量条
- 状态 = 剖面图顶部常驻的系统状态条

**优点**：系统化概念强（三层架构直接变界面）、无平铺 tab、信息密度靠层级。
**风险**：剖面图对普通用户可能抽象；需要清晰的展开/收起动效。

---

## 概念 B · 能力核心 + 轨道（Core & Orbits）

**一句话**：中央是 Agent OS 核心，能力围绕核心轨道分布，选中即聚焦。

**主视图**：中央一个核心（显示系统状态），周围一圈轨道节点——
运行时（python/node）是较大的节点，组件是较小节点，空间/状态是外围信息环。
点节点 → 该节点放大到主视图，显示版本/安装/操作。
安装新能力 = 轨道上出现新节点（带入场动效）。

**四类内容**：
- 商店 = "发现"手势从核心拉出可用能力节点
- 组件 = 轨道上的节点本身
- 空间 = 外环容量指示（节点大小/环粗细反映占用）
- 状态 = 核心颜色/脉动

**优点**：最有"操作系统"气质、视觉独特、关系（依赖）可用节点连线表达。
**风险**：移动端 393dp 上节点图易拥挤；需要克制，否则变花哨；可达性/可访问性较难。

---

## 概念 C · 序列工作台（Sequential Workbench）

**一句话**：不是"首页/商店/组件"并列，而是"选运行时 → 装组件 → 配应用"的线性工作流。

**主视图**：一条纵向的"配置序列"，每一步是一站：
```
1 运行时   python 3.14.8 已选 →  [切换版本]
2 工具链   cmake ✓  git ✓  →  [添加工具]
3 空间     603MB / 364GB 可用
4 系统     运行中 · 控制面在线
```
每步是一个横向卡片，展开后是详细管理（版本列表/工具列表）。
底部是全局命令栏（搜索/执行），贯穿所有步骤——借鉴命令总线但不作为主页。

**四类内容**：
- 商店 = 第1/2步展开后的"添加"视图
- 组件 = 第2步
- 空间 = 第3步
- 状态 = 第4步 + 顶部常驻状态条

**优点**：符合用户真实心智（先有运行时再装工具）、线性易理解、移动端友好。
**风险**："系统状态"放最后可能弱化；需要让非流程性的查看（如体检）有入口。

---

## 三概念对比

| | A 剖面房 | B 能力核心 | C 序列工作台 |
|---|---|---|---|
| 系统化概念 | 三层架构=界面 | OS 核心+轨道 | 配置流水线 |
| 视觉独特性 | 中 | 高 | 中 |
| 移动端适配 | 好 | 中 | 好 |
| 信息完整 | 好 | 中 | 好 |
| 实现成本 | 中 | 高 | 低 |
| 与传统 tab 区别 | 大 | 最大 | 中 |

我的建议：A 或 C。A 最能体现"Agent OS 三层架构"的产品定位，C 最实用且移动端友好。
B 视觉最独特但移动端风险高，可作为 A 的首屏局部视觉语言（核心+状态环）而非整体结构。
